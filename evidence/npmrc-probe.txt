3. WHAT THE BUNDLE SAYS (read before running, to know what to expect)
================================================================================
From pnpm.mjs, ../exec/commands/lib/runDepsStatusCheck.js:

    const { upToDate, issue, workspaceState } = await checkDepsStatus(opts3);
    if (upToDate === true) return;
    if (upToDate === void 0 && opts3.allProjects == null
        && opts3.rootProjectManifest == null) return;
    const command = ["install", ...createInstallArgs(workspaceState?.settings)];
    const install2 = runPnpmCli.bind(null, command, {...});
    switch (opts3.verifyDepsBeforeRun) {
      case "install": install2(); break;
      case "prompt":  ... (throws if !process.stdin.isTTY) ...
      case "error":   throw new PnpmError("VERIFY_DEPS_BEFORE_RUN", issue ?? ...)
      case "warn":    ...
    }

and in the `pnpm run` handler:

    if (opts3.verifyDepsBeforeRun) { await runDepsStatusCheck(opts3); }

So `error` MUST throw when deps are not up to date. If a run with `error` set
performs an install instead, the only possible explanation is that the value
never reached opts.verifyDepsBeforeRun.

8. WHAT WAS AND WAS NOT OBSERVED
================================================================================
OBSERVED:
  - node_modules presence/absence and entry count, listed before and after
    every run.
  - pnpm-lock.yaml sha256 before and after every run — never changed once.
  - pnpm store: file count under store\v11\files, 60016 before and after the
    stale-dep runs.
  - pnpm's own per-run accounting ("downloaded 0" on every install that ran).
  - wall-clock: the refusing and warning runs took ~0.5s, far too short for
    registry resolution.

NOT OBSERVED / LIMITS:
  - Store file COUNT is not a content hash. A same-count in-place rewrite would
    not have been caught. No packages were reported downloaded, and left-pad
    never appeared, so the claim made here is "no packages entered the store by
    this measure", not "the store is bit-identical".
  - No packet capture was taken. "Did not reach the network" is inferred from
    downloaded-0, unchanged store, and sub-second timing — not measured
    directly. The one run that provably WOULD have gone to the network
    (section 6) was stopped by the offline flag, and its error names the
    registry mirror it wanted.
  - pnpm's update notifier printed "Update available! 11.17.0 -> 11.24.0" during
    the first install. That is a cached/periodic check; whether it made a
    request during these runs was not determined.
  - Section 5 required node_modules to exist. The brief's "sandbox must have no
    node_modules" could not hold for the genuine-dep-staleness experiments,
    because without node_modules pnpm can only report "cannot check" and never
    reaches a real dependency verdict. FINDING, per the brief: pnpm created
    node_modules in the sandbox by itself, on the very first `pnpm run probe`,
    while `verify-deps-before-run=error` was set in .npmrc. That creation was
    not requested and is itself the proof that the .npmrc key is inert. All 73
    packages came from the local store, downloaded 0.
  - This probe does NOT prove interception of the 2026-08-25 incident's exact
    path. That incident's staleness had a different cause (it added importer
    entries for @deepseek-ai/cordis and @deepseek-ai/schemastery, packages
    already in the tree), not a dependency missing from the lockfile. What is
    proven is the detection-and-response semantics of the setting, and where
    the setting has to live for those semantics to apply at all.


================================================================================
9. BOTTOM LINE
================================================================================
  - `error` genuinely refuses on a real stale dependency: exit 1, script never
    runs. PROVEN.
  - `warn` genuinely warns and runs without installing: lockfile, store and
    node_modules all unchanged. PROVEN.
  - Both of the above only hold when the setting is in pnpm-workspace.yaml or
    in pnpm_config_verify_deps_before_run.
  - In .npmrc — where this repo puts it — pnpm ignores it and falls back to its
    default `install`, and will spawn a network install from a plain
    `pnpm run <script>`. PROVEN, section 6.
  - Therefore this repo is, as of this probe, still exposed to the failure mode
    its .npmrc was written to prevent.

in scope here) and is left to the Executor Lead: move `verifyDepsBeforeRun:
