## NEW FINDING — outboundConsumed is not a bearer for "egress went out"

This is the substantive result of the run, and it contradicts what the first
draft of this file asserted.

`preexecute.ts:402-427` bumps `outboundConsumed` (and emits `consume-manifest`)
ONLY when `next()` returns a non-error result, precisely so that the counter
means "egresses that ACTUALLY went out", and so that "archived with no
consume-manifest" is readable as authorized-but-not-dispatched. That
distinction did not survive contact with the runtime: all four commands FAILED
(exit 1, no ref moved) and the counter still reached 4, with a
`consume-manifest` event for each.

Cause: `isErrorResult` (`preexecute.ts:154-157`) keys on `isError === true` on
the result object. The dsh pwsh tool does not set that flag for a command that
exits non-zero, so a failed shell command is indistinguishable from a
successful one at this seam. The counter therefore bears "dispatched, and the
runtime did not flag an error" — NOT "the egress went out". Any downstream
reader (including this package's own closeout prose) that treats
`outboundConsumed > 0` as proof that text left the machine is reading a
property the counter cannot observe.

And the shape does not discriminate in the other direction either — an earlier
draft of this file said error-producing wrappers make the not-dispatched case
distinguishable, which is wrong: a later wrapper may dispatch the command,
reach the remote, and only then throw or return an error result, producing
exactly the same archive-without-event shape as a cancellation that preceded
dispatch. The error shape alone proves NOTHING about whether the command was
dispatched. Only a cancellation independently known to precede dispatch tells
you that, and nothing in this capture establishes one.

## STILL UNPROVEN after this run (do not cite this file as closing these)

- **Outbound forward dispatch with a genuinely successful transport.** Nothing
  here shows a real egress completing. The residual stays open, and closing it
  needs a host whose shell channel actually works, or a channel other than the
  broken pwsh fork path.
- **`approval: native` answered by a real human / the governance property.**
  The four "Allow once" clicks were performed by the driving AGENT through the
  browser under the owner's blanket authorization for this task. Blanket
  authorization does not convert an automated UI action into a human answer.
  What is borne is the mechanical ask -> allow route; who answered is NOT.
  Closing this needs the owner to answer the prompt themselves.
- **owner-approve passthrough (`autopilot_signal action=owner-approve`).**
  Blocked in this deployment for a reason worth recording: the signal call is
  itself issued through the run_code channel, whose text is matched verbatim,
  and the call text carried `note: "git push"`. The manifest did not declare
  that substring, so the authorization call self-tripped the egress gate. On a
  direct (non-run_code) tool channel this would not occur, but that was not
  driven here.
